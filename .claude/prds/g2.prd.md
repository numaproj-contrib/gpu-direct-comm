# vertexDomainController — MultiNetwork Pod 間名前解決 (G2)

## Problem
G1 で numaNetwork CRD + Mutating Webhook + custom webhook provider (IPAM) により、Pipeline デプロイ時に Vertex Pod へ Secondary NIC と IP アドレスが自動付与される仕組みが成立した。しかし、送信元の UDF コンテナが送信先 Pod の Secondary NIC IP を知る手段が存在しない。Kubernetes 標準の Service / DNS は Primary NIC（Pod IP）のみを対象としており、Secondary NIC IP は名前解決できない。この状態では MultiNetwork 上の Pod 間データ転送（将来の GPU Direct RDMA 含む）を開始できず、G1 で構築したネットワーク基盤が活用できない。

## Evidence
- チーム内設計レビューで合意済み（Confluence「アクセラレータ間直接通信 STEP2設計」）
- G1 の成果として Secondary NIC + IP 割当が成立しつつあり、次の障壁が「送信先の Secondary NIC IP 発見」であることが明確化
- Kubernetes 標準 DNS（CoreDNS）は Pod IP / Service ClusterIP のみを登録対象とし、Secondary NIC IP を扱う仕組みが存在しない（MultiNetwork Subproject が将来的に標準化を議論中だが、現時点では利用不可）

## Users
- **Primary**: Numaflow で GPU アクセラレータパイプラインを構築する Platform Engineer。Pipeline マニフェストをデプロイするだけで、Secondary NIC 上の名前解決が自動的に成立することを期待する。
- **Not for**: CPU 単独 Vertex パイプラインのユーザ（Secondary NIC 不要）。クラスタ管理者（etcd / CoreDNS の初期セットアップは前提作業として別担当が実施）。

## Hypothesis
We believe **vertexDomainController による Secondary NIC IP の CoreDNS etcd 登録** will **MultiNetwork 上の Pod 間名前解決を実現し、RDMA 直接通信の前提を確立する** for **Numaflow Pipeline をデプロイする Platform Engineer**.
We'll know we're right when **UDF コンテナから vertexDomain FQDN で DNS クエリを実行し、送信先 Pod の Secondary NIC IP が返ること** を E2E テストで確認できる。

## Success Metrics
| Metric | Target | How measured |
|---|---|---|
| vertexDomainController による DNS レコード登録 | Pod 作成から 30s 以内に etcd にレコード反映 | E2E テスト |
| UDF コンテナからの名前解決成功 | vertexDomain FQDN → Secondary NIC IP が返る | E2E テスト（`getaddrinfo` 等） |
| Pod 削除時の DNS レコード削除 | Pod 削除から 30s 以内にレコード消去 | E2E テスト |
| 既存 Pipeline（numaNetwork 未使用）への非破壊性 | 既存 E2E 全通過 | CI |

## Scope
**MVP** — vertexDomain ラベルの Pod 付与 + vertexDomainController（Pod 作成監視 → ResourceClaimStatus から Secondary NIC IP 取得 → 専用 etcd へ DNS レコード登録・削除）+ CoreDNS etcd プラグイン設定 + UDF コンテナからの名前解決 E2E 検証。

**Out of scope**
- GPU Direct RDMA 送受信の実装 — G3 で実装
- NumaflowSDK 拡張（DNS クエリ API / RDMA 送受信 API）— G3 で実装
- Gateway API ベースの第2案（独自 CR 群による MultiNetwork 通信）— CoreDNS etcd 方式が成立しない場合の fallback として保留
- マルチクラスタ対応 — 単一クラスタ内での名前解決に限定
- 専用 etcd / CoreDNS の HA 構成 — 開発段階では単一インスタンスで十分
- Vertex Controller の upstream 改変 — vertexDomain ラベル付与は外部コントローラまたは Webhook で対応（upstream 提案は別途）

## Open Questions
- [x] vertexDomain ラベルを誰が付与するか — M1 で外部 Mutating Webhook (VertexDomainMutator) を採用。M4 で Label はマーカー化し FQDN は Annotation に移行予定（ADR-003）
- [ ] vertexDomain FQDN の仕様確定 — `<vertex>.<numaNetwork>.<pipeline>.<namespace>.vertexdomain.local` は暫定。ドメイン階層の順序や TLD の妥当性を検証
- [x] CoreDNS etcd プラグインの k3d 上での動作実績 — M2 で検証完了。etcd サーバブロック追加方式を採用（ADR-002）
- [x] 専用 etcd のデプロイ方式 — M2 で単一 Pod + ClusterIP Service として手動デプロイを採用（ADR-002）
- [ ] ResourceClaimStatus.AllocatedDeviceStatus.NetworkDeviceData.Addresses の k8s バージョン依存 — KEP-4817 は k8s 1.36 で stable 予定だが、開発環境の k8s バージョンとの整合

## Risks
| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| CoreDNS etcd プラグインが期待通り動作しない（設定複雑、k3d 環境での制約） | Medium | High | 早期に PoC 検証。不成立なら第2案（Gateway API 風 CR）に切り替え |
| ResourceClaimStatus から Secondary NIC IP を取得できない（k8s バージョン・DRA 実装の制約） | Medium | High | G1 M5 の E2E で ResourceClaimStatus の利用可能性を先行確認 |
| vertexDomain FQDN のドメイン階層が DNS 規約と衝突 | Low | Medium | RFC 準拠を確認。`.local` は mDNS 予約だが、クラスタ内 CoreDNS では問題ないことを検証 |
| 専用 etcd の運用負荷（障害時の DNS 解決不能） | Medium | Medium | MVP は単一インスタンス。本番向け HA は Out of scope として後送 |
| Vertex Controller の改変なしに vertexDomain ラベルを付与する手段の制約 | Medium | Medium | Mutating Webhook で Pod 作成時にラベル注入する方式を第一候補とし、upstream 提案は並行で進める |
