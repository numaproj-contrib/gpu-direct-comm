## Summary

M3 で Pipeline annotation に宣言された edge↔numaNetwork 束縛を、Mutating Webhook で
Pipeline の `spec.vertices[].resourceClaims` に ResourceClaimTemplate（RCT）参照として注入する。
numaflow のコードは一切改変せず、既存の伝播経路
（Pipeline Controller → Vertex 生成 → `ApplyToPodSpec` → Pod `spec.resourceClaims`）に乗せることで、
DRA が Secondary NIC を Vertex Pod に割り当てる経路を確立する。

annotation の無い既存 Pipeline は素通り（Allow + パッチなし）し、非破壊性を維持する。

## 注入のデータモデル

numaflow の `AbstractVertex` は `AbstractPodTemplate` を `json:",inline"` で埋め込んでいるため、
`resourceClaims` は vertex JSON の直下に現れる:

```json
{
  "spec": {
    "vertices": [
      {
        "name": "filter-resize",
        "resourceClaims": [
          {
            "name": "pipeline1-multi-network-rct",
            "resourceClaimTemplateName": "pipeline1-multi-network-rct"
          }
        ]
      }
    ]
  }
}
```

`PodResourceClaim` の `name` は Pod 内でユニークな識別子。RCT 名と同じ `<numaNetwork.name>-rct` を使う。

## Tasks

### Task 1: Mutating Webhook ハンドラの実装
- **Action**: `internal/webhook/v1alpha1/pipeline_mutator.go` に controller-runtime の `admission.Handler` を実装する
  - `PipelineMutator` 構造体（`Client client.Client`, `Scheme *runtime.Scheme`）
  - `Handle(ctx, req) admission.Response`:
    1. `req.Object.Raw` を `unstructured.Unstructured` にデコード
    2. annotation `gpu-direct-comm.numaproj.io/numa-network-edges` を取得。**無ければ `admission.Allowed`（パッチなし）**
    3. `ParseBindings()` でパースし、`connectionType: direct` の束縛のみ対象
    4. `spec.vertices[]` を走査し、各束縛の `from` / `to` に名前一致する vertex を特定
    5. 該当 vertex の `resourceClaims` 配列に `{"name": "<nn>-rct", "resourceClaimTemplateName": "<nn>-rct"}` を追加（重複排除）
    6. 変更後の unstructured を marshal し、`admission.PatchResponseFromRaw(req.Object.Raw, patched)` で JSON Patch レスポンスを返す
  - kubebuilder マーカー: `// +kubebuilder:webhook:path=/mutate-numaflow-numaproj-io-v1alpha1-pipeline,mutating=true,failurePolicy=fail,sideEffects=None,groups=numaflow.numaproj.io,resources=pipelines,verbs=create;update,versions=v1alpha1,name=mpipeline.numaproj.io,admissionReviewVersions=v1`
  - **注入ルール**（ADR-0009）:
    - `connectionType: direct` の場合のみ注入
    - 束縛の `from` と `to` **両方**の vertex に RCT 参照を追加（edge の両端が Secondary NIC を持つ必要がある）
    - 同一 vertex が複数束縛に関与する場合は重複排除
- **Mirror**: `pipeline_webhook.go` の `PipelineValidator.Handle` パターン
- **Validate**: `go build ./internal/webhook/...`

### Task 2: Mutating Webhook ハンドラのユニットテスト（RED → GREEN）
- **Action**: `internal/webhook/v1alpha1/pipeline_mutator_test.go` に table-driven テスト。既存の `buildWebhookScheme` / `newNumaNetwork` / `makeRequest` ヘルパーを再利用。`pipelineJSON` は vertex 付きに拡張するか、新ヘルパーを追加:
  - **(a) annotation 無し → Allowed、patches なし**（非破壊性）
  - **(b) 有効な束縛 → Allowed、from/to 両 vertex に resourceClaims パッチが入る**
    - パッチ適用後の JSON を検証: `spec.vertices[].resourceClaims` に `{"name":"<nn>-rct","resourceClaimTemplateName":"<nn>-rct"}` が存在
  - **(c) 複数束縛で同一 vertex が重複 → resourceClaims に重複なし**
  - **(d) vertex に既存 resourceClaims がある場合 → 追記（既存を消さない）**
  - **(e) connectionType が direct でない束縛 → その束縛は注入スキップ**（Validating 側で弾かれるが、Mutating 側でも安全に無視）
- **Mirror**: `pipeline_webhook_test.go` の AAA・table-driven パターン
- **Validate**: `go test -race ./internal/webhook/... -run TestPipelineMutator`

### Task 3: main.go への Mutating Webhook 登録
- **Action**: `cmd/main.go` に Mutating Webhook を登録する。既存の Validating Webhook 登録の直前に配置:
  ```go
  mgr.GetWebhookServer().Register(
      "/mutate-numaflow-numaproj-io-v1alpha1-pipeline",

          Client: mgr.GetClient(),
  ```

## Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| `admission.PatchResponseFromRaw` が unstructured の再 marshal で予期しないフィールド順序変更を起こす | Low | controller-runtime が JSON Patch (RFC 6902) を自動生成するため、フィールド順序は無関係。テストでパッチ適用後の値を検証する |
| 同一 vertex に既存 `resourceClaims` がある Pipeline で注入が上書きする | Low | 既存エントリを保持し追記する実装にする。Task 2 (d) で検証 |
| Mutating Webhook が Pipeline の spec を書き換えるため、`kubectl diff` で差分が出る | Low | 許容。annotation を付けたユーザの意図した動作。将来の upstream 化で annotation → spec first-class フィールドに移行する際に解消 |
| `failurePolicy: Fail` により webhook 不可用時に annotation 付き Pipeline の apply が失敗する | Medium | ADR-0009 の設計判断: annotation 付き Pipeline が「注入されないまま通る」方が危険なため Fail を採用。運用上は replicas + readiness で可用性を確保 |
| numaflow が `AbstractPodTemplate` から `ResourceClaims` フィールドを削除した場合、pruning で注入が消える | Low | numaflow v1alpha1 に定義済み（`pod_template.go:99`）。upstream バージョン更新時に確認する（PRD Risks に記載済み） |
